### 5. DIGIFLAZZ_INTEGRATION_GUIDE.md
**Scope:** Implementation-level guide for all Digiflazz interactions, including authentication, error handling, retry policies, webhook verification, and sync scheduler design.
**Key sections:**
- Credential storage pattern: apiKey in Vault at path `secret/digiflazz/api_key`, rotated quarterly
- HMAC signature generation (MD5 for request, HMAC-SHA1 for webhook verification)
- Request builder code snippet (Go) with timestamp and nonce
- Error mapping table: Digiflazz RC → internal error code (enum) → user-friendly Indonesian message
  - RC 01/70: TRANSIENT_ERROR (retry after 2s, max 3 attempts)
  - RC 68: OUT_OF_STOCK (display "Stok habis, coba produk lain")
  - RC 85: RATE_LIMIT (display "Silakan coba dalam 1 menit")
  - RC 44: INSUFFICIENT_DIGIFLAZZ_BALANCE (alert admin)
- Webhook implementation:
  - HMAC-SHA1 validation using shared secret from Vault
  - Replay attack protection: store processed `ref_id` + event sequence, reject duplicates
  - Webhook retry: return 200 immediately on success; on 5xx, Digiflazz retries for 72 hours
  - Ping event handling: respond with 200 and echo `sed` parameter
- Product sync scheduler design:
  - Cron: prepaid hourly (minute 5), postpaid every 5 minutes (cron: */5 * * * *)
  - Use Redis distributed lock with 10min TTL to prevent overlapping runs
  - Delta sync strategy: fetch all, upsert by `buyer_sku_code`, archive discontinued products (soft delete `is_active=false`)
  - Rate limit respect: only 1 pricelist query per 5 min (Digiflazz RC 83), stagger calls
  - Backoff: on RC 83, wait 4 min before retry; on network error, exponential backoff to 30min max
- Transaction initiation:
  - Idempotency: check `Idempotency-Key` header, store mapping before calling Digiflazz
  - Retry logic: if RC 01/70/99, wait 1s, 2s, 4s then give up; display "Sedang diproses, tunggu sebentar"
  - Payload validation: customer_no format per product category regex
- Monitoring: expose `/health/digiflazz` endpoint that calls `Cek Deposit` to verify connectivity
**Dependencies:** SECURITY_ARCHITECTURE.md (webhook secret), TRANSACTION_STATE_MACHINE.md (RC→state mapping)
**Effort:** 2 days

### 6. BUSINESS_LOGIC_SPEC.md
**Scope:** All business rules, formulas, validation logic, and edge-case decisions.
**Key sections:**
- Pricing formula definitions:
  - `platform_price = base_price + platform_markup` (platform_markup stored as DECIMAL(5,2) percentage, e.g., 0.05 = 5%)
  - `mitra_profit = selling_price - platform_price` (enforced: ≥ 0, reject if selling_price < platform_price)
  - `staff_commission` calculation:
    - FixedAllowance: fixed_amount per transaction
    - MarginShare: `(selling_price - platform_price) × staff_percentage / 100` (default 60%)
    - Commission recorded in `transactions.staff_commission_amount` (new column needed)
- Wallet rules:
  - Mitra main wallet: `is_main_wallet=true`, no parent
  - Staff wallet: `is_main_wallet=false`, `parent_wallet_id` references Mitra's wallet
  - Top-up: Mitra wallet must have sufficient balance; atomic transfer using DB transaction
  - Overdraft: forbidden (balance >= 0 enforced)
  - Freeze: wallet can be `frozen` boolean flag; frozen wallets reject transactions
- Role assignment validation:
  - Only Mitra can assign Staff role
  - Staff can only be assigned by one Mitra (enforced by `assigned_by` foreign key + check constraint)
  - User cannot be Staff of multiple Mitras simultaneously (business rule: one staff → one mitra)
  - Self-assignment prohibited (user cannot assign Mitra role to self)
- Transaction validation flow:
  - Pre-transaction: wallet balance check, product active check, staff daily limit check
  - During: Digiflazz call with timeout 30s
  - Post: webhook expected within 2min; if not received, auto-poll using `Cek Status` after 10min
- Margin Settings structure change: Split `staff_margin_settings` into two tables:
  - `staff_global_margin_settings` (mitra_id, staff_id, scheme_type, value, UNIQUE(mitra_id, staff_id))
  - `staff_product_margin_overrides` (mitra_id, staff_id, product_id, scheme_type, value, UNIQUE(mitra_id, staff_id, product_id))
  - On commission calculation: check product override first, fall back to global
- Daily transaction limits (fraud detection):
  - Staff default limit: 50 transactions/day OR Rp 5,000,000 daily turnover (configurable per staff)
  - Enforcement: check `transactions` count where `user_id=staff AND DATE(created_at)=CURRENT_DATE` before allowing new transaction
  - Exceeded limit: return error TRANSAKSI_DAILY_LIMIT with message "Daily limit reached, contact Mitra"
- Multi-role switching behavior:
  - Active role determines which wallet is debited
  - Transaction history is global across roles (show all, but filterable by role)
  - Commission attribution: staff commission tied to staff_role transaction, visible in staff view regardless of active role
- Postpaid inquiry validity:
  - Inquiry result valid for 24h only; after that, must re-inquire
  - Stored in `postpaid_inquiries` table with `expires_at` timestamp; on pay, validate not expired
- Refund handling (if Digiflazz refunds):
  - Webhook event type `refund` received → credit staff wallet immediately
  - Mitra wallet untouched (refund from Digiflazz goes to platform, not directly to Mitra)
  - Commission reversal: if staff already earned commission, issue negative commission entry
**Dependencies:** Concurrency design, error mapping, state machine
**Effort:** 2 days

### 7. DATA_MODEL_VALIDATION.md
**Scope:** Field-level validation rules, database-level constraints, application-level checks, and data integrity invariants.
**Key sections:**
- Validation matrix per table (users, wallets, transactions, products, otp_codes, staff_margin_settings)
- Database constraints SQL (CHECK, NOT NULL, UNIQUE, FOREIGN KEY with ON DELETE/UPDATE actions):
  - `users.phone_number` format:印尼格式 regex `^\\+62[0-9]{8,12}$`
  - `wallets.balance >= 0` (CHECK constraint)
  - `transactions.amount >= 0`, `selling_price >= amount`
  - `products.platform_price >= base_price`
  - `staff_margin_settings.value` bounds: scheme 'MarginShare': 0-100 (%); 'FixedAllowance': 0-1000000
- Application validation flow (before DB write):
  - Password: min 8 chars, 1 uppercase, 1 lowercase, 1 digit
  - PIN: exactly 6 digits, numeric only, cannot be sequential (123456, 654321 forbidden)
  - Phone number: validate format, check uniqueness
  - OTP: 6-digit numeric, expires in 5 minutes, max 3 verification attempts before invalidate
- Business invariants (must always hold true):
  - Sum of staff wallet balances ≤ Mitra main wallet balance (enforced by application logic on every top-up)
  - Each transaction's `selling_price - platform_price ≥ 0` (profit non-negative)
  - Total staff commission across all staff ≤ total platform profit
  - Audit logs never modified/deleted (append-only, maybe `ON DELETE RESTRICT`)
- Data consistency checks (cron jobs):
  - Daily wallet reconciliation: sum(wallet_events) = sum of wallet balances
  - Orphan detection: transactions with non-existent wallet_id, product_id
  - Negative balance detection and alert
**Dependencies:** Business logic spec, concurrency patterns
**Effort:** 1.5 days

### 8. API_AUTHENTICATION_FLOW.md
**Scope:** Detailed authentication and authorization flows including device trust, token refresh, PIN changes, role switching.
**Key sections:**
- End-to-end request flow diagrams (Mermaid sequence diagrams)
- Normalized login endpoint design: single `POST /auth/login` with adaptive behavior based on device trust
- Device fingerprinting algorithm: collect 6 signals (user agent, device ID hash, IP subnet, app version, install date, last login timestamp) → compute score (0-100); ≥70 = trusted
- Trusted device database: `device_fingerprints` table with `is_trusted`, `trust_score`, `last_used_at`
- JWT claims structure: `sub` (user_id), `role` (active_role_id), `roles` (array of all role_ids), `wallet_id` (active wallet_id), `device_id` (fingerprint ID), `exp`, `iat`
- Token refresh flow: `POST /auth/refresh` with refresh token (stored in Redis allowlist with 7d TTL); refresh rotates refresh token (one-time use)
- Revocation: logout adds refresh token to Redis blocklist until expiry
- PIN change flow: re-authentication required (password + OTP) before allowing PIN update
- Role switching: `POST /users/switch-role` validates user has that role, updates JWT claim in new token issued via refresh (or returns new access token directly)
- Session management: inactive for 30min → forced logout; configurable per role
- Multi-device login: allowed (each device gets its own refresh token and device fingerprint); concurrent sessions tracked (max 5 devices per user); anomaly alert if >5
- Password reset flow: `POST /auth/forgot-password` → OTP to phone → set new password
- Compromised PIN handling: after 3 failed PIN attempts, lock account for 1 hour, require password + OTP to unlock
**Dependencies:** Security architecture, error handling
**Effort:** 1.5 days

### 9. MOBILE_APP_SPEC.md
**Scope:** Requirements specific to Flutter mobile client: offline mode, push notifications, biometrics, local storage, data sync, performance.
**Key sections:**
- Offline-first strategy:
  - Local database: Hive (NoSQL) for transactions, products cache, user profile
  - Write queue for transaction initiation when offline: store locally, mark `pending_sync`, sync on connectivity restore with exponential backoff and conflict resolution (last-write-wins with user confirmation if timestamp differs >5min)
  - Product catalog cache: TTL 1 hour, soft-invalidate on app foreground
- Push notifications (FCM):
  - Message types: `transaction_success`, `transaction_failed`, `low_balance_warning` (balance < Rp 10,000), `staff_added`, `topup_received`
  - Payload format (data-only messages with routing): `{ "type": "...", "transaction_id": "...", "amount": "...", "deep_link": "/transactions/..." }`
  - Notification channels: `transactions` (default), `alerts` (high priority), `staff` (lower)
- Biometrics:
  - Supported: fingerprint, face ID (via local_auth Flutter plugin)
  - Enabled per user preference (opt-in)
  - Fallback to PIN on biometric failure (3 attempts)
  - Biometric key stored in secure enclave/Keystore, never leaves device
- Local storage security:
  - Hive encrypted box with key derived from user PIN (argon2id, 64-byte salt per user stored on server)
  - Sensitive tokens: access_token in memory only, refresh_token encrypted in Hive
- Data synchronization:
  - Pull-to-refresh pattern on all list screens
  - Pagination: 20 items per page, infinite scroll with cursor-based pagination (`created_at` + `transaction_id` cursor)
  - Optimistic UI: show transaction immediately as "Processing" before server ack
- Performance budgets:
  - Cold start: <2s on mid-range Android (2019+), <1.5s iOS
  - APK size: <50MB (split APK per ABI, exclude unused locales)
  - Memory: <150MB typical, <300MB peak
- Network layer:
  - Dio HTTP client with interceptors: auth token injector, refresh token logic, request retry with backoff, logging toggle
  - Timeouts: connect 10s, receive 30s
  - Connection pooling: keep-alive, max 4 concurrent connections
- UI state management: Riverpod with StateNotifier; each screen a StateNotifier provider; error state separate from data state
- Crash reporting: Sentry with PII redaction; user_id attached to events for correlation
**Dependencies:** None (standalone client spec)
**Effort:** 2 days

### 10. ERROR_HANDLING.md
**Scope:** Comprehensive error code system, mapping from Digiflazz RC to internal codes, retry policies, user-facing messages (Indonesian), client error display patterns.
**Key sections:**
- Error taxonomy:
  - `AUTH_*` (authentication failures: invalid credentials, expired token, account locked)
  - `TRANSACTION_*` (transaction errors: insufficient balance, product unavailable, pending limit, timeout)
  - `DIGIFLAZZ_*` (upstream errors mapped by RC code)
  - `RATE_LIMIT_*` (too many requests)
  - `VALIDATION_*` (input format errors)
  - `SYSTEM_*` (internal server errors)
- Full mapping table `digiflazz_rc_map`:
  ```
  RC  | Internal Code        | User Message (ID)                      | Retry? | TTL
  00  | SUCCESS              | "Transaksi berhasil"                   | No     | -
  01  | DIGIFLAZZ_TIMEOUT    | "Timeout, silakan coba lagi"           | Yes (3x)| 2s
  03  | PENDING              | "Transaksi sedang diproses"            | Yes (poll)| 30s
  44  | INSUFFICIENT_BALANCE | "Saldo platform tidak cukup"           | No     | -
  68  | OUT_OF_STOCK         | "Stok produk habis"                    | No     | -
  85  | RATE_LIMIT           | "Terlalu banyak permintaan, coba 1 menit lagi" | Yes (backoff) | 60s
  ```
- Retry policy matrix (per error category):
  - Network errors: exponential backoff (1s, 2s, 4s, 8s) — max 4 attempts
  - Digiflazz transient (RC 01, 70): immediate retry same endpoint, max 3 attempts with 2s interval
  - Rate limit (RC 85): respect `Retry-After` header if present; else wait 60s; max 1 retry
  - Idempotency violation (duplicate ref_id): return 409 Conflict, no retry
- Client-side error display:
  - Toast notifications for transient errors (auto-dismiss 3s)
  - Modal dialogs for blocking errors (insufficient balance, invalid PIN)
  - Inline form errors (below input field, red text)
  - Empty state + CTA for no internet
- API error response standard format:
  ```json
  {
    "error": {
      "code": "INSUFFICIENT_BALANCE",
      "message": "Saldo tidak mencukupi",
      "details": {
        "current_balance": 25000,
        "required": 50000,
        "wallet_id": "uuid"
      },
      "trace_id": "abc123" // for support
    }
  }
  ```
- Logging requirements: every error logged with full context (user_id, endpoint, request_id) to structured logger
- Support integration: `trace_id` provided to user for support tickets; admin panel search by trace_id shows full request/response
**Dependencies:** Digiflazz RC mapping, business logic
**Effort:** 1.5 days
