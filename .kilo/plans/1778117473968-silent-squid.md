# PPOB Monolith to Microservices Migration Plan

**Target Architecture:** 6 independent microservices deployed on Kubernetes  
**Timeline:** 6-8 weeks (2-3 sprints)  
**Risk Level:** HIGH — requires careful data consistency and transaction coordination  
**Team:** Backend engineers (3), DevOps (1), QA (1)

---

## Executive Summary

This plan outlines the phased migration from a monolithic Go application (single binary, shared database) to a distributed microservices architecture. The monolith currently handles authentication, users, wallets, transactions, products, and Digiflazz integration in one process. The target state separates these concerns into independent, scalable services with eventual consistency and resilience patterns.

### 2.2 Extract Auth Service (Week 2)

**Scope:** `/auth/v1/*` endpoints only

**Migration Steps:**
1. Create `cmd/auth-service/main.go`
2. Move `internal/handler/auth_handler.go` → `auth-service/internal/handler/`
3. Move `internal/service/auth_service.go` → `auth-service/internal/service/`
4. Move `internal/repository/auth_repository.go` → `auth-service/internal/repository/`
5. Copy database config, connection pool
6. **Keep monolith** — run both simultaneously
7. Add **API Gateway** (NGINX/Kong) to route:
   - `/auth/v1/*` → Auth Service
   - All other routes → Monolith
8. Verify all auth flows work correctly
9. **Decouple:** Auth Service gets its own DB connection (shared DB instance)

**Key Decision:** Authentication tokens must be valid across all services → implement JWT with shared public key or token introspection endpoint.

### 2.3 Extract User Service (Week 2-3)

**Scope:** `/users/v1/*` endpoints

**Steps:**
1. Create `cmd/user-service/main.go`
2. Extract User & Role management logic
3. **Challenge:** Staff/role assignment requires wallet creation
   - Keep wallet creation in User Service for now
   - Or call Wallet Service via gRPC during user registration
4. Add routing: `/users/v1/*` → User Service
5. **Shared DB:** Continue using shared PostgreSQL (no schema changes)

**Data Consistency:** Use **Saga Pattern** for multi-step operations:
```
User Registration Saga:
1. User Service: Create user record → PUBLISH "UserCreated"
2. Wallet Service: Consume event → Create wallet → PUBLISH "WalletCreated"
3. Auth Service: Consume event → Create auth credentials
```

### 2.4 Extract Wallet Service (Week 3)

**Scope:** `/wallets/v1/*` endpoints

**Critical:** Must handle concurrent debit/credit safely

**Implementation:**
1. Create `cmd/wallet-service/main.go`
2. Move wallet balance and hold logic
3. **Isolation:** Own `wallets` and `wallet_events` tables (consider schema duplication or shared access)
4. **Event Sourcing:** All balance changes via `wallet_events` table (already implemented)
5. Expose events: "WalletDebited", "WalletCredited", "HoldPlaced", "HoldReleased"

**Concurrency Control:** Keep **pessimistic locking** (SELECT FOR UPDATE) within Wallet Service

### 2.5 Extract Transaction Service (Week 3-4)

**Most Complex — coordinates multiple services**

**Scope:** `/transactions/v1/*` endpoints, Digiflazz integration

**Dependencies:**
- Needs to call Wallet Service (debit/hold)
- Needs product info from Product Service
- Needs user validation from User Service
- Needs to emit events for commissions

**Pattern:** **Orchestration Saga**

```go
func (s *TransactionService) Initiate(ctx context.Context, req TransactionRequest) error {
    // 1. Validate product (call Product Service)
    product, err := s.productClient.GetProduct(ctx, req.ProductID)
    
    // 2. Check/hold wallet balance (call Wallet Service)
    holdResp, err := s.walletClient.PlaceHold(ctx, &wallet.HoldRequest{
        UserID:    req.UserID,
        Amount:    req.SellingPrice,
        Reference: req.TransactionID,
    })
    if err != nil {
        return err // insufficient funds
    }
    
    // 3. Create transaction record (local DB)
    tx := &models.Transaction{...}
    
    // 4. Call Digiflazz (async or sync)
    digiResp, err := s.digiClient.InitiateTransaction(ctx, ...)
    
    if digiResp.RC == "00" { // Immediate success
        // 5. Debit wallet (convert hold to debit)
        s.walletClient.ConvertHoldToDebit(ctx, holdResp.HoldID)
        // 6. Calculate and credit commission
        s.emitCommission(tx)
    } else if digiResp.RC == "03" { // Pending
        // Hold remains until webhook
    } else { // Failed
        // 7. Release hold
        s.walletClient.ReleaseHold(ctx, holdResp.HoldID)
    }
}
```

**Compensation:** On failure, publish `TransactionFailed` event → Wallet Service releases hold

**Decision Matrix:**
| Criteria | gRPC | REST |
|----------|------|------|
| Performance | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| Complexity | ⭐⭐ | ⭐⭐⭐⭐ |

## Phase 4: Distributed Data Management (Week 5-6)

### 4.1 Database Strategy

**Phase 1 (Immediate): Shared Database, Separate Schemas**
- All services connect to same PostgreSQL instance
- Each service owns its tables (no cross-service table access)
- Foreign keys between service tables are **removed or made optional**
- Service A reads Service B data via API calls, not DB joins

**Phase 2 (Future): Database-per-Service**
- Each service gets its own DB instance
- Requires data replication or event-driven updates
- Use **Change Data Capture (CDC)** for cross-service data sync

### 4.2 Handling Shared Tables

**Problem:** `user_roles` table used by User Service AND Auth Service for authorization

**Solution A: Data Duplication (Eventual Consistency)**
```
User Service (owns user_roles)
    │
    └── publishes "RoleAssigned" event
        │
        ▼
Auth Service (has user_roles_copy)
    └── consumes event → updates local cache
```

**Solution B: API-Based (Stronger Consistency)**
- Auth Service calls User Service API to check roles
- Cache results in Auth Service (Redis) with TTL
- Pro: Always accurate, Con: Adds latency, coupling

**Recommendation for PPOB:** **API-based** for authorization (low latency requirement, strong consistency needed)

### 4.3 Transaction Coordination

**Problem:** Creating a transaction involves:
1. Check wallet balance (Wallet Service)
2. Place hold (Wallet Service)
3. Call Digiflazz (Integration Service)
4. Update transaction status (Transaction Service)
5. Debit wallet on success (Wallet Service)
6. Calculate commission (Transaction Service)

**Pattern: Saga with Orchestration**

```go
// Transaction Orchestrator (in Transaction Service)
type TransactionSaga struct {
    steps []SagaStep
}

func (s *TransactionSaga) Execute(ctx context.Context) error {
    for i, step := range s.steps {
        if err := step.Execute(ctx); err != nil {
            // Execute compensation in reverse order
            for j := i - 1; j >= 0; j-- {
                s.steps[j].Compensate(ctx)
            }
            return err
        }
    }
    return nil
}

// In InitiateTransaction handler:
saga := NewTransactionSaga(req)
if err := saga.Execute(ctx); err != nil {
    return fmt.Errorf("transaction failed: %w", err)
}
```

**Saga Steps:**
1. `ValidateProductStep` (calls Product Service)
2. `PlaceHoldStep` (calls Wallet Service)
3. `ExecuteTransactionStep` (calls Integration Service)
4. `DebitWalletStep` (calls Wallet Service) — compensation: ReleaseHold
5. `CreateCommissionStep` (internal)

### 4.4 Event-Driven Architecture

**Use Kubernetes-native: Redis Streams or NATS**

**Sample Event Flow:**
```
Transaction Service --"TransactionSuccess"--> [Redis Stream]
                                                    ↓
Wallet Service (consumer) -- credits commission --> [Wallet updated]
                                                    ↓
Notification Service (async) --> sends push notification
```

**Implementation:**
```go
// Publisher (Transaction Service)
```

## Phase 5: Observability & Resilience (Week 6-7)

### 5.1 Distributed Tracing

**All services must:**
1. Generate/propagate `trace_id` in every request
2. Export spans to Jaeger
3. Log with `trace_id` for correlation

**OpenTelemetry Setup (each service):**
```go
func initTracer() func() {
    // Create Jaeger exporter
    exp, err := jaeger.New(jaeger.WithCollectorEndpoint(
        jaeger.WithEndpoint("http://jaeger-collector:14268/api/traces"),
    ))
    
    // Create trace provider
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exp),
        sdktrace.WithResource(resource.NewWithAttributes(
            semconv.SchemaURL,
            semconv.ServiceName("wallet-service"),
        )),
    )
    
    otel.SetTracerProvider(tp)
    return func() { tp.Shutdown(ctx) }
}

// In HTTP middleware:
func TracingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()
        
        // Extract trace context from headers
        sc := otel.GetTextMapPropagator().Extract(ctx, otelhttptrace.Extract(ctx, r))
        
        // Create span
        _, span := otel.Tracer("http-server").Start(sc, r.URL.Path)
        defer span.End()
        
        // Add to context and proceed
        r = r.WithContext(ContextWithSpan(ctx, span))
        next.ServeHTTP(w, r)
    })
}
```

### 5.2 Circuit Breaker

**Use:** `github.com/sony/gobreaker`

```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "WalletService",
    MaxRequests: 5,  // requests allowed when half-open
    Interval:    1 * time.Minute,
    Timeout:     30 * time.Second,  // stay open before trying
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        // Trip if >50% failures in last 20 requests
        failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
        return counts.Requests >= 20 && failureRatio > 0.5
    },
})

func (c *Client) PlaceHold(ctx context.Context, req *HoldRequest) (*HoldResponse, error) {
    result, err := cb.Execute(func() (interface{}, error) {
        // Make gRPC call
        return c.client.PlaceHold(ctx, req)
    })
    if err != nil {
        return nil, err
    }
    return result.(*HoldResponse), nil
}
```

### 5.3 Retry with Backoff

```go
func withRetry[T any](op func() (T, error), maxRetries int, initialDelay time.Duration) (T, error) {
    var zero T
    delay := initialDelay
    
    for i := 0; i <= maxRetries; i++ {
        result, err := op()
        if err == nil {
            return result, nil
        }
        
        if i == maxRetries {
            return zero, fmt.Errorf("max retries exceeded: %w", err)
        }
        
        time.Sleep(delay)
        delay *= 2  // exponential backoff
    }
    return zero, nil
}

// Usage:
balance, err := withRetry(func() (float64, error) {
    return walletClient.GetBalance(ctx, userID)
}, 3, 100*time.Millisecond)
```

## Phase 7: Data Migration (Week 8)

### 7.1 Database Schema Refactoring

**Changes Needed:**

1. **Remove foreign keys between service-owned tables**
   - `wallet_events.wallet_id` → no foreign key to `wallets` (Wallet Service owns both anyway)
   - `transactions.wallet_id` → no foreign key (cross-service)
   - `user_roles.user_id` → soft foreign key (optional constraint)

2. **Add audit columns to all tables**
   ```sql
   ALTER TABLE transactions ADD COLUMN IF NOT EXISTS created_by UUID;
   ALTER TABLE transactions ADD COLUMN IF NOT EXISTS updated_by UUID;
   ALTER TABLE transactions ADD COLUMN IF NOT EXISTS created_from_service VARCHAR(50) DEFAULT 'transaction-service';
   ```

3. **Duplicate read-optimized tables** for performance
   - `transaction_summaries` (denormalized view for listing)

### 7.2 Migration Script

**Strategy:** Dual-write during transition

```go
// In monolith (before full cutover)
func CreateTransaction(tx *models.Transaction) error {
    // Write to monolith DB
    err := monolithDB.Create(tx).Error
    
    // Also publish event for new services
    eventBus.Publish("transaction.created", tx)
    
    return err
}

// New Transaction Service consumes and writes to its own DB (idempotent)
func HandleTransactionCreated(event TransactionCreatedEvent) {
    // Check if already exists (idempotency)
    if exists := txRepo.Exists(event.ID); exists {
        return
    }
    txRepo.Create(event.Transaction)
}
```

**Cutover Steps:**
1. Run migration: Add columns, remove foreign keys, create indexes
2. Deploy new services alongside monolith (dual-write)
3. Switch API Gateway routes gradually (5% → 50% → 100%)
4. Monitor for 1 week
5. Decommission monolith endpoints
6. Remove dual-write code
7. Final verification and cleanup

## Phase 8: Rollback & Contingency Plan

### 8.1 Rollback Triggers
- Error rate >5% sustained for 30 minutes
- Data inconsistencies detected
- Performance degradation p99 >2s
- Wallet balance discrepancies

### 8.2 Rollback Procedures

**Partial Rollback (per service):**
1. Update API Gateway to route traffic back to monolith for affected endpoints
2. Disable new service (scale to 0)
3. Analyze logs, fix issue
4. Redeploy

**Full Rollback:**
1. Route ALL traffic to monolith via load balancer
2. Disable all new microservices
3. Stop dual-write
4. Restore DB from backup if corruption detected
5. Conduct post-mortem

**Rollback Automation:**
```bash
#!/bin/bash
# rollback.sh
kubectl patch ingress ppob-ingress -p '
{"spec":{"rules":[{"http":{"paths":[
  {"path":"/","backend":{"serviceName":"monolith","servicePort":8080}}
]}}]}}'
echo "Traffic routed to monolith"
```

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Distributed Transaction Failure** | Critical | Implement Saga pattern with compensation, idempotent operations, circuit breakers |
| **Data Inconsistency** | Critical | Event sourcing, reconciliation jobs, alerts on drift, DB constraints where possible |
| **Network Partitions** | High | Timeouts, retries, circuit breakers, degrade gracefully (e.g., show cached data) |
| **Performance Degradation** | Medium | Caching layer (Redis), database indexes, async processing for non-critical paths |
| **Service Discovery Failure** | Medium | Kubernetes DNS fallback, static config fallback, health checks |
| **Team Skill Gap** | Medium | Training, pair programming, start with simpler services, incremental approach |
| **Extended Deployment Window** | Low | Blue-green deployments, canary releases, feature flags |
